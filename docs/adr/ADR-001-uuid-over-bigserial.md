# ADR-001: UUID over BIGSERIAL for Primary Keys

**Status:** Accepted  
**Date:** 2026-08-01  
**Deciders:** Engineering

---

## Context

Every table needs a primary key. The two mainstream options in PostgreSQL are:

- `BIGSERIAL` — auto-incrementing 64-bit integer, generated by a database sequence
- `UUID v4` — 128-bit random identifier, generated in application code or by `gen_random_uuid()`

This is a SaaS platform that will eventually serve many construction companies
(organizations). We expect to shard data or federate reads by organization as
we scale. We also expose resource IDs in REST URLs (`/api/v1/projects/{id}`).

---

## Decision

Use `UUID` (v4, generated by PostgreSQL's `gen_random_uuid()`) as the primary
key for every table.

```python
id: Mapped[uuid.UUID] = mapped_column(
    UUID(as_uuid=True),
    primary_key=True,
    server_default=text("gen_random_uuid()"),
)
```

---

## Rationale

### 1. No ID leakage in URLs

`/projects/1`, `/projects/2`, `/projects/3` tells a competitor exactly how
many projects you have created. `/projects/f3a2b1c0-...` leaks nothing.
Indian construction SMBs are competitors with each other — this is not
hypothetical.

### 2. Multi-tenancy is safer

With sequential integers, a misconfigured query that forgets the
`organization_id` filter can accidentally return another tenant's row with
ID `42`. With UUIDs, guessing a valid foreign-key value at random is
computationally infeasible. Defense in depth.

### 3. Application-generated IDs enable offline / pre-flight use

When a site engineer creates an indent on a tablet with intermittent signal,
the mobile app can generate the UUID locally, show it to the user, and sync
later. With BIGSERIAL, you must round-trip to the database to learn the ID
before you can reference it in linked records.

### 4. Merge-friendly in future federation scenarios

If we ever shard by `organization_id` across PostgreSQL instances, or federate
data from a field device into the cloud, UUID primary keys merge without
conflict. BIGSERIAL sequences per-shard collide.

### 5. `gen_random_uuid()` is a built-in

PostgreSQL 13+ includes `gen_random_uuid()` as a core function (no extension
required). The performance difference vs. a sequence is negligible for our
write rates.

---

## Alternatives Considered

| Option | Why Rejected |
|---|---|
| `BIGSERIAL` | Sequential IDs leak enumeration info; shard merges collide; client can't pre-allocate IDs |
| `UUID v7` (time-ordered) | Not natively available in PostgreSQL without extension; index locality benefit is marginal at our scale |
| `ULID` | No native PostgreSQL type; would require storing as `TEXT` or `BYTEA`, complicating queries |
| Application-side `uuid4()` | `server_default=gen_random_uuid()` means the DB always sets it even if the ORM forgets — safer default |

---

## Consequences

### Positive
- No ID guessing attacks across tenants
- Mobile / offline ID pre-allocation is possible
- No cross-shard conflicts if we ever federate

### Negative
- UUID indexes are larger than integer indexes (~16 bytes vs 8 bytes)
- Random UUIDs cause index bloat and worse cache locality than sequential keys
  (mitigated: our write volume is not high enough for this to matter; revisit
  if we exceed ~10M rows per table)
- UUIDs are less readable in logs and debugging — mitigated by always logging
  them alongside human-readable fields (`project_name`, `email`)

---

## Review Trigger

Revisit this decision if:
- Any single table exceeds 50M rows and we observe measurable index bloat
- We adopt a write-heavy time-series workload (attendance logs, sensor data)
  where insert-order locality would provide a measurable throughput gain
